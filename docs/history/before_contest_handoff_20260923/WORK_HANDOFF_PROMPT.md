## 2. PSLogの基本

PSLogはWindows向けアマチュア無線ログソフト。
Python + PySide6 + PyInstaller。

PSLog TXT:
DATE｜TIME｜BAND｜MODE｜HIS CALLSIGN｜RTSs｜RTSr｜HIS QTH｜MY QTH｜RMKS｜JCCJCG
11項目固定、UTF-8 BOM + CRLF。

RMKS2はRMKS欄内に
RMKS1 <<RMKS2>> RMKS2
として保存する。

Windowsビルド、PySide6 GUI、EXE実機確認はユーザー側。
Linux環境では非GUIテスト、構文、データ整合性、ZIP適用確認等をできる限り実施する。

## 4. 最重要設計原則

「コンテスト提出時の機械判定」と「人間向けルール表示」は役割を分ける。

### 提出側で比較的厳しく判定するもの
客観的・機械的に判断でき、提出データの正当性に直接関係する事項:
- 対象バンド逸脱
- 対象モード逸脱
- 採点
- マルチ計算
- 必須フィールド
- 移動運用時のOPPLACE欠落
- 明確な参加部門条件との矛盾
- 同一QSOの不正な重複
- 提出ファイル形式上の必須事項

### 必要以上に提出拒否しないもの
規約解釈、実運用、外部ソフト挙動等が絡む事項までPSLogが過剰に弾かない。
特にインターネット、クラスター、セルフスポット、ソフトウェア、
リバースエンジニアリング、事後ネット掲載、ログソフト固有機能等を
安易に確認チェックや提出不可条件へ追加しない。

### その代わりルール表示を正確にする
ユーザーがルール表示を読めば公式規約を正しく把握できることを重視する。

愛・地球博記念コンテストの `rule_view` を表示品質の基準とする。

最低限確認する表示項目:
1. 参加できる局
2. 送信出力
3. 移動運用
4. 呼び出し方法
5. 交信対象
6. 周波数制限
7. 交信上の禁止・制限
8. コンテストナンバー交換
9. 同一局との再交信条件

大会固有の時間制限・10分ルール・特殊局条件等があれば必要に応じて追加表示する。

表示データを増やしたことを理由に提出ロジックを自動的に厳しくしてはいけない。

## 5. 表示品質の基準

愛・地球博記念コンテストの現行表示を基準にする。

- 公式規約長文をそのまま貼らず、意味を変えず読みやすく整理
- 内部略語・機械翻訳調の文章を避ける
- 呼び出し方法、交信対象、周波数、禁止・制限、ナンバー、重複条件等を明示
- 公式規約にない解釈を追加しない

XPO記念コンテストでは現行PSLogが「呼び出し方法未登録」となっているが、
公式規約には
- 電信: CQ XPO TEST
- 電話: CQ XPOコンテスト
がある。
XPOだけでなく87大会全体を確認する。

## 7. rule_view構造

現在、愛・地球博だけがrule_view 9項目を明示的に完備。
他大会は提出・採点用データやフォールバック表示に依存している。

提出用 `required_flags` / `required_fields` / score設定 / 内部フラグ名から
呼び出し方法や規約文章を推測しない。

表示用データは公式規約を根拠に独立して保持する。

## 8. 確認事項チェックの恒久方針

「確認事項（全て確認して要チェック）」へ何でも追加しない。

確認チェックは参加部門、運用条件、得点、提出可否に直接関係し、
明示確認する実務的意味があるものに絞る。

原則追加しないもの:
- 一般的遵守条項
- インターネット利用禁止
- クラスター利用禁止
- ソフトウェア関連
- リバースエンジニアリング
- 事後ネット掲載禁止
- 解釈で揉めやすい事項

ただし公式規約表示本文として事実を表示することは別。
「表示」と「確認チェック」を混同しない。

## 9. OPPLACE既存方針

移動運用時はOPPLACE必須。

固定運用でも常時OPPLACE必須として現在認めているのは:
- オール千葉
- オール兵庫
- KCJ
- KCJトップバンド

ルール表示調査を理由に不要な常時必須を再追加しない。

## 11. 作業目的

この作業は規約を厳しく取り締まるためではない。

「PSLogが必要以上に提出を拒否しない一方で、
ユーザーがルール表示を見れば正しい規約情報を把握できる」

状態を作ることが目的。

公式規約を忠実に調査し、表示の正確性を最優先する。
推測で埋めるより、不明点を明示して残す方を優先する。
