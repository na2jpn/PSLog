# インポート・QSL受領一括の中断回復（1.00）

原本の書き換え前に、全保存先のバックアップと回復記録を作成します。
bak/batch_recovery/*.pending.jsonには原本の変更前ハッシュ、変更後の全バイト、
結果JSON/CSVの最終内容、処理途中で出力する結果ファイルの許容ハッシュを保存します。
QSLは従来どおり最初の結果CSVが正常保存されるまで原本を更新しません。
最終CSVには更新前の初回QSL確認・BURO発送記録なし・当該交信のMY QTHを保持します。

処理途中で停止した場合、同じ入力を再実行せず「ログを再読込」を使ってください。
再起動後の自局ログ読込、および次のlogbook書き込み用ロック取得時も回復を試みます。
元の入力ファイルを読み直すのではなく、保存済みの変更後内容を反映します。
そのため「全て追加」でも回復を繰り返したことによる二重追加は起きません。
意図的に新たなインポートを全追加で実行すれば、従来どおり重複も追加します。

回復前に、全原本と全結果ファイルを照合します。原本は記録した変更前/後、
結果はその処理が実際に書こうとした内容に一致する場合だけ続行します。
外部編集、削除、読込不能などがあれば止まり、回復記録の場所を表示します。
結果をUSB等に保存していた場合、その保存先を同じ場所で利用可能にしてから再読込してください。
外部変更時は現行ログ・結果・回復記録を保全して比較する必要があります。
競合の対話的解決画面は未実装。pendingの削除で強制解除しないでください。

原本→結果ファイルの順で最終状態へ揃え、完了後にdone.jsonへ改名します。
途中のCSVが「処理中・成否要確認」のままなら、復旧完了までは確定結果と扱わないでください。
出力障害が続く場合は未完了記録を残して停止します。初期CSVの保存やバックアップに失敗して
まだ回復記録を作っていなければ、原本変更はありません。原因解消後に再確認できます。

これは複数ファイルの同時原子更新ではなく、保存済みの処理を完了させる回復方式です。
既存の年変更回復も継続します。回復済み履歴は自動削除しません。
旧版で作られたimport結果JSONやQSL journal.jsonだけでは変更後の全内容が不足するため、
今回の方式で旧中断処理を自動復旧しません。

全体ZIPバックアップはconfig/logbookが対象で、bakの回復履歴と外部結果CSVは含みません。
ただしバックアップ開始時のlogbookロックで未完了を先に回復し、回復不能なら作成を止めます。

## 開発検証
158テスト成功（Linux Qt offscreen）。新規3件に加え既存の中断試験を拡張。
・全追加・複数年インポートで入力ファイル削除後も回復し、繰り返しても重複しない。
・結果ファイルが外部変更されたら原本へ一切反映せず停止。
・原本保存後に結果保存で停止しても、次回回復で結果を最終状態へ更新。
・既存インポート部分失敗試験を再インポートから回復方式へ変更。
・QSL部分保存後の回復で更新前フラグ、MY QTH、最終保存状態を維持。
